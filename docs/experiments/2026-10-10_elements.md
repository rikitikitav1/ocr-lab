# 2026-10-10 - Assembling a chapter's elements

Lead: a chapter is read by both engines, Docling and MinerU, and the assembler builds one reading from
them, using only the book itself: the PDF's text layer, the agreement of the engines, glyph advances. It
never sees a gold. The measurements ask how close that gets to the better engine on each element (code,
tables, headings, prose), one pass at a time, under a gate written before the run.

## Setup

**Set** rag-lab `converter_gold`, text-PDF sections: 112 declared, 95 scored, then **91**; each a cut PDF
with a hand-made Markdown gold, scored per element by `POST /v1/eval/elements`
(`app/evaluation/element_run.py`). 45 prose, 40 code and 27 table sections from English progit, postgres,
python, django and ares, and Russian progit, postgres, latex_baldin and haskell_kholomiev. **Engines**
Docling, MinerU, assembled, and `best_of_both`, a per-column oracle that may take two columns from two
readings of one place (a ceiling only).

Pinned:

- Docling `default.json` (tesseract OCR on, code and formula enrichment off, heading hierarchy) with
  `to_formats=json`; MinerU `ocr_mode=txt`, tier standard, `middle_json`; both through this stand's
  adapters and Markdown writer with no rule, on the fields rag-lab uses for text PDFs.
- Output cut to the section by the PDF outline (title to the next entry at its level or above), not by
  either engine's headings: MinerU sets every title at level 2.
- Scored per element: code blocks exact and contained, table cells found (multiset), headings found and
  phantom, plain-text similarity, word F1, running-head lines left in the body. Formulas and images are
  counted, not scored (two gold files of each).
- Guards on the gold, added after the first run: 16 sections whose gold came from another section with
  the same title and 1 without a gold were set aside by `gold_in_layer` below 0.75 (95 left); a guard on
  the layer lines inside the gold's own boxes, `gold_clip_f1` below 0.6, set aside 4 more (two
  two-column clips of ares, a django release note, a three-word latex gold): 91 left.

The gate of the page referee, written before its run and used for every pass after it: columns per
section `code_contained`, `code_exact`, `cells_found`, `headings_found`, `body_f1` (higher is better),
`code_out_foreign`, `headings_phantom` (lower is better). Pass rule: on every section the assembled
reading is not worse than the better single engine on any column; every section where it is worse is
listed with column, size and reason. Tolerance 0 on counts, -0.01 on `body_f1`.

Eye check (a model reviewer, Claude Sonnet, 8 sections): MinerU preferred on 6, Docling on 2. Docling
flattens multi-line code to one line (5 of 8), drops empty table cells so the cells after them shift
columns (the postgres feature matrix, ares), lost one paragraph on ares, set a caption after its table.
MinerU lost part of one block (postgres ru: CREATE TABLE and VIEW gone, GRANT kept), doubles or drops
backslashes in LaTeX code, leaves one-line commands unfenced, made `$ ghci` a heading, split a python
table into row fragments, puts stray spaces inside words and read `Ø` as `∅`. Running heads: 1 leak per
engine on 95 sections, so furniture is not a problem on text PDFs.

Decision: no default changed. Fix plan: (1) code lines flattened (Docling): code text from the layer
inside the block's box; (2) one-line commands read as prose (both engines): a code pass by monospace
glyphs; (3) the table cell grid (Docling): per table, the reading whose cells cover the layer's words
better; (4) code lost or garbled inside a block (MinerU; latex, postgres): layer text again; (5) phantom
headings (postgres run-in heads, django): per book, the heading pass preferring toc sub-entries.
Left for book knobs: LaTeX backslashes, the `∅` glyph, two columns on ares.

table from one engine with code from the other. The gate also had a check that does not use the gold: the
referee's picks on the 8 eye-checked sections against the reviewer's.

Decision: the referee stays as the floor and the source of prose and headings; the code and table passes

### Code from the text layer, and monospace paragraphs as code

## Caveats

- The oracle `best_of_both` peeks at the gold and mixes columns. It bounds a choice between two
  readings, not a pass that reads text from the layer: code from the layer later went past it.
- Formulas and images are not scored. The set has one two-column book (ares), two of whose sections the
  second guard set aside; no rule here targets two-column layout, so the engines own it and
  ares_en_prose_00 shows what that costs.
- The eye rounds are one model reviewer on 8 sections: a check from outside, not a score.
- Between 1178 and 1432 the scorer changed: a tag was matched across lines from any `<` (code `<-`, `<*>`,
  `a < b`), now only a named tag on one line outside fences. 32 rows' similarity and F1 moved by up to 2
  points, no total moved.
- The first real book run (book 38, PostgreSQL Notes for Professionals) showed a code block split into
  several fences where an engine drew several boxes on one page; the join across pages does not cover it.
  On book 111 (Romanian prose of 1905) no code pass fired in any chapter, while on book 38 they fired
  (counts 187, 31 and 10): the passes select themselves by the face on the page.
- The monospace test is by glyph advances only, with no font names; a book that sets code in a
  proportional face (latex_baldin) is outside it.
- Broken hyphens in cells (21) are counted, not repaired. Agreement with the layer needs a layer: on a
  scanned range the table choice has no evidence and tables come from the recognising engine.
